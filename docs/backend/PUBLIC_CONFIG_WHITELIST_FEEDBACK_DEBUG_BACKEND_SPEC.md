# ТЗ: Публичный конфиг, whitelist, feedback и дебаг-массовое создание дней (бэкенд)

**Версия:** 1.1  
**Аудитория:** Backend developer  
**Контекст:** Сейчас часть этих операций выполняется из мобильного приложения через **Directus SDK** с **сервисной учёткой** (email/password в бинарнике). Цель — **убрать сервисный логин с клиента** и отдать данные/операции через **Pivot Backend API**.

Связанные документы: `docs/backend/DAY_ENTITY_BACKEND_SPEC.md` (модель дня), `docs/backend/FRONTEND_AUTH_AND_OTP.md` (JWT).

---

## 1. Цели

1. Отдать **app config** и **accounts whitelist** с бэкенда **без требований к «защите»** в смысле авторизации пользователя (см. раздел 5).
2. Принять **feedback** на бэкенде и **сохранить в Directus** (коллекция `feedback`). **Вложения и файлы не обрабатываются** в рамках этого ТЗ.
3. Реализовать **вспомогательную дебаг-ручку** для **массового создания 200 дней** для пользователя (эквивалент текущего `createMany` по коллекции `day` из клиента).

---

## 2. Источник данных (Directus)

Ориентир по именам коллекций и полям — как в клиенте (`lib/core/services/directus/directus_collections.dart`):

| Ресурс        | Коллекция Directus   | Примечание |
|---------------|----------------------|------------|
| App config    | `appConfig` (prod) / `debugAppConfig` (debug-сборки в клиенте) | Бэкенд может читать **одну** каноническую коллекцию по окружению |
| Whitelist     | `accountsWhiteList`  | Один singleton-документ (в клиенте `readOne('1')`) |
| Feedback      | `feedback`           | Создание записи без файлов |
| История дней  | `day`                | Массовое создание |

Конкретные поля схемы Directus — сверить с админкой; ниже — **минимальный контракт ответа/запроса**, совместимый с текущим использованием во Flutter.

## 3. API

Базовый URL — как у существующего User Service (см. `UserServiceClient`). Пути ниже **предлагаемые**; можно сгруппировать под префиксом `/v1/…` по принятому стандарту проекта.

### 3.1 `GET /config/app` (или `/public/app-config`)

**Назначение:** отдать содержимое app config **как в Directus** (или суженный projection), чтобы клиент перестал вызывать `readAppConfig()` через SDK.

**Авторизация:** **не требуется** (публичный endpoint).  
**Rate limiting:** рекомендуется лёгкий лимит с IP, чтобы не ддосить Directus.

**Ответ 200:** JSON-объект с полями, которые сегодня читает приложение, например:

- `inceptionDate` — используется в расчёте Pivot Life Score (int ms или ISO string — **как сейчас в Directus**).
- Иные поля из `appConfig`, если UI/логика завязаны (версии, флаги и т.д.) — **прозрачный pass-through** из Directus или явный список полей в OpenAPI.

**Ошибки:** 502/503 при недоступности Directus.

---

### 3.2 `GET /config/accounts-whitelist` (или `/public/accounts-whitelist`)

**Назначение:** отдать данные белого списка для проверки email (см. `AccountsWhiteListServiceImpl`).

**Авторизация:** **не требуется** (публичный endpoint).  
**Rate limiting:** по IP.

**Ответ 200:** JSON, **совместимый** с тем, как парсит клиент. Сейчас в коде есть расхождение путей (`whiteListData['list']['list']` vs `whiteListData['list']`) — на бэкенде зафиксировать **одну каноническую форму**, например:

```json
{
  "emails": ["a@b.com", "c@d.com"]
}
```

либо сохранить структуру из Directus 1:1 и **обновить клиент** под неё в отдельной задаче. В ТЗ для бэка: **документировать выбранную форму** в OpenAPI.

**Ошибки:** при отсутствии записи — 200 с пустым списком или 404 — **выбрать одно поведение** и описать.

---

### 3.3 `POST /feedback`

**Назначение:** создать запись обратной связи в Directus (`feedback`), заменив клиентский `directus.createOne(feedbackCollection, …)`.

**Тело запроса (JSON):** поля, соответствующие текущему `FeedbackModel.toJson()` во Flutter:

| Поле                 | Тип     | Обязательность |
|----------------------|---------|----------------|
| `authorName`         | string  | да |
| `authorDirectusId`   | string \| null | нет (гость / не залогинен) |
| `email`              | string  | да |
| `subject`            | string  | да |
| `message`            | string  | да |

**Вложения:** **не принимать и не обрабатывать**. Если клиент пришлёт лишние поля (`media`, `files`) — **игнорировать**. Multipart — **не поддерживать** в этой версии (415 или играть как JSON-only).

**Авторизация:** по решению команды:

- **Вариант A (простой):** публичный POST + rate limit + антиспам (captcha позже).
- **Вариант B:** если передан `Authorization: Bearer <access>` — опционально валидировать JWT и доверять `authorDirectusId` из токена, а не из тела.

Зафиксировать выбранный вариант в OpenAPI.

**Ответ 201:** созданная сущность или `{ "id": "..." }`.

**Ошибки:** 400 валидация, 429, 5xx.

**Прямое требование:** после внедрения ручки **не** писать в Directus из приложения сервисной учёткой для feedback.

---

### 3.4 `POST /debug/days/seed-history` (или `/internal/...`)

**Назначение:** создать **до 200** записей `day` для указанного пользователя — аналог дебаг/онбординг-потока `UserBloc` (`createMany` по `day`).

**Тело запроса (JSON):**

| Поле      | Тип    | Обязательность |
|-----------|--------|----------------|
| `userId`  | string | да — Directus user id (`x-user-id` семантика) |
| `count`   | int    | нет, по умолчанию **200**, максимум **200** |

**Правила генерации полей дня** — на бэкенде реализовать **эквивалент** клиентской логики «исторические дни» (см. `UserBloc._addHistoryDays` / `_createHistoryDaysSync`):

- Даты: от **вчера** назад на `count` дней.
- Поля в Directus — как при клиентском `DayEntity.toDirectus(userId)`:
  - `userId`
  - `macros` (объект)
  - `healthMetrics` (объект)
  - `dateTime` — **строка с миллисекундами эпохи** (как в клиенте)
  - `weekTdeeAverage`, `mealPlan`, `chatSnap`, `cycleId`, `welnessEntity` — по той же семантике, что клиент кладёт в мок-историю (пустой снап, `requestsLeft: 13`, и т.д.).

**Идемпотентность:** явно описать: повторный вызов **создаёт дубликаты** или бэкенд проверяет уникальность `(userId, dateTime)` — **выбрать** (рекомендация: уникальный индекс в Directus + отказ с 409 или пропуск существующих).

**Авторизация и окружение (обязательно жёстко):**

- Ручка **только** для non-production **или** защищена секретом (`pivot-identity-key` + allowlist service) **и** опционально флагом `ENABLE_DEBUG_SEED=true`.
- **Запрещено** оставлять без защиты в проде.

**Ответ 200/201:** `{ "created": <number>, "userId": "..." }`.

**Ошибки:** 400, 403, 404 (user not found).

## 4. Миграция клиента (вне scope бэка, но ожидание)

После готовности API:

- Заменить вызовы `DirectusService.readAppConfig` → `GET /config/app`.
- Заменить `readAccountsWhiteList` → `GET /config/accounts-whitelist` (с учётом финальной формы JSON).
- Заменить `FeedbackRepositoryImpl.sendFeedback` → `POST /feedback` без загрузки файлов; UI не должен ожидать успешную привязку медиа.
- Дебаг «200 дней» → вызов `POST /debug/days/seed-history` при включённом дебаг-режиме.
- Удалить сервисный Directus login из приложения, когда все оставшиеся прямые вызовы SDK будут закрыты **отдельными задачами**.

## 5. Безопасность (резюме по требованиям заказчика)

| Endpoint              | Авторизация по требованию |
|-----------------------|---------------------------|
| App config            | **Публично**, без защиты в смысле user auth |
| Whitelist             | **Публично**, без защиты в смысле user auth |
| Feedback              | Определить (см. 3.3); файлы не обрабатывать |
| Seed 200 days         | **Строго ограничить** (дебаг/internal/не прод) |

---

## 6. Не входит в объём

- Загрузка файлов feedback, коллекция `feedbackFiles`, связи many-to-many с `directus_files`.
- Отдельная коллекция «строк дневника питания» в Directus не используется в продукте; дневник и велнес лежат в сущности **`day`** (`welnessEntity`, `PATCH /days/current` и т.д.).

---

## 7. Критерии приёмки

1. Без авторизации доступны публичные `GET` для app-config и whitelist; ответы стабильны и задокументированы.
2. `POST /feedback` создаёт запись в Directus из JSON; вложения не требуются.
3. Дебаг-ручка создаёт до 200 дней для `userId` и **не доступна** в production без явной отдельной политики (или недоступна совсем в прод).
4. OpenAPI/Swagger или внутренний док с примерами запросов/ответов и кодами ошибок.
