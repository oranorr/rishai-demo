# ТЗ: OAuth (Google / Apple) и выдача JWT на бэкенде

Документ для бэкенд-разработки: **вход через Google и Apple** с **криптографической верификацией** токена провайдера и выдачей той же пары **`access_token` / `refresh_token`**, что и после [`POST /auth/verify-otp`](./FRONTEND_AUTH_AND_OTP.md).

Контекст по заголовкам, JWT и публичным эндпоинтам — в [FRONTEND_AUTH_AND_OTP.md](./FRONTEND_AUTH_AND_OTP.md).

---

## 1. Цель

1. Убрать доверие к телу вида «вот email и provider» без проверяемого доказательства идентичности (текущий `POST /users/login-oauth` с полями `email`, `name`, `provider` при общем `pivot-identity-key`).
2. После успешного OAuth клиент должен получать **те же JWT**, что и после email+OTP, чтобы дальнейшие запросы шли только с **`Authorization: Bearer <access_token>`** (и при необходимости refresh), без привязки к статическому ключу на устройстве.

---

## 2. Текущее состояние (клиент, ориентир)

- На устройстве: нативный вход (Google / Apple) → **Firebase Auth** (`signInWithCredential`).
- После этого мобильное приложение вызывает **`POST /users/login-oauth`** с JSON `{ email, name, provider }` и заголовком **`pivot-identity-key`**.
- **Firebase ID token (или id token провайдера) на бэкенд не передаётся** — идентичность на сервере фактически не верифицируется.

Целевое состояние: **один публичный эндпоинт** (см. §4), принимающий **проверяемый токен**, возвращающий **ту же форму**, что `verify-otp` / `refresh`.

---

## 3. Рекомендуемый подход к верификации

### Вариант A (рекомендуется при текущем клиенте с Firebase)

Клиент после `signInWithCredential` получает **Firebase ID token** (`getIdToken()` в Firebase SDK).

Бэкенд:

- Использует **Firebase Admin SDK** (или эквивалент) и метод **`verifyIdToken(idToken)`**.
- Из декодированных claims извлекает минимум:
  - стабильный идентификатор пользователя: **`uid`**;
  - способ входа: например **`firebase.sign_in_provider`** (`google.com`, `apple.com`, …);
  - **`email`** (если есть) и флаг верификации email, если доступен в claims.

**Плюсы:** одна точка проверки для Google и Apple, не нужно отдельно тянуть JWKS Apple/Google на первом этапе.

**Требования к конфигурации:** на бэке сервисный аккаунт Firebase / credentials (JSON или переменные окружения), **тот же Firebase project id**, что у мобильных приложений.

### Вариант B (альтернатива)

Прямая верификация **Google ID token** и **Apple identity token** по OIDC/JWKS провайдеров (отдельная логика на `iss` / `aud` / `sub` / `exp`, для Apple — учёт **`sub`** как основного ключа, **nonce** при необходимости).

Имеет смысл, если хотите **не зависеть от Firebase** на сервере.

## 4. Контракт API

### 4.1. Новый публичный эндпоинт

Маршрут должен быть в том же классе исключений, что **`/auth/request-otp`**, **`/auth/verify-otp`**, **`/auth/refresh`**: **без** обязательного **`pivot-identity-key`** и **без** Bearer до выдачи токенов.

Предлагаемое имя (можно согласовать в коде):

| Метод | Путь | Назначение |
|--------|------|------------|
| `POST` | `/auth/oauth` | Обмен проверенного токена провайдера (через Firebase или напрямую) на пару JWT. |

### 4.2. Тело запроса (минимум)

Рекомендуемый JSON (поля можно уточнить при реализации):

```json
{
  "id_token": "<Firebase ID token JWT string>",
  "provider_hint": "google"
}
```

- **`id_token`** — обязателен: строка JWT для `verifyIdToken` (если выбран вариант A).
- **`provider_hint`** — опционален: подсказка для логов/метрик; **доверять для безопасности нельзя** — источник истины после верификации — claims (в Firebase — `sign_in_provider`).

Опционально (если бэк создаёт пользователя при первом входе и нужно имя):

```json
{
  "id_token": "...",
  "display_name": "..."
}
```

Для Apple имя часто приходит только при первом показе окна на клиенте — клиент может передавать его один раз; бэк не должен требовать его для повторных входов.

### 4.3. Успешный ответ

Идентичен ответу **`POST /auth/verify-otp`** и **`POST /auth/refresh`** (см. [FRONTEND_AUTH_AND_OTP.md §3](./FRONTEND_AUTH_AND_OTP.md)):

```json
{
  "success": true,
  "access_token": "<JWT>",
  "refresh_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 900
}
```

При необходимости в том же ответе можно вернуть фрагмент профиля (как раньше в `login-oauth`) — **отдельно согласовать** с фронтом; минимально достаточно JWT + **`GET /users/me`** с Bearer.

### 4.4. Ошибки

Тот же конверт, что в [FRONTEND_AUTH_AND_OTP.md §7](./FRONTEND_AUTH_AND_OTP.md).

Рекомендуемые коды (пример):

| `code` | Когда |
|--------|--------|
| `UNAUTHORIZED` / `INVALID_TOKEN` | Невалидная подпись, истёкший токен, неверный `aud`/`iss`. |
| `FORBIDDEN` | Токен валиден, но провайдер не разрешён политикой (если введёте allowlist). |
| `VALIDATION_ERROR` | Нет `id_token`, пустое тело. |

## 5. Доменная логика на бэкенде

1. **Верифицировать** `id_token` (Firebase Admin или OIDC).
2. **Смаппить** внешнюю идентичность на внутреннего пользователя (Directus / ваша модель):
   - рекомендуемый ключ: **`(provider, external_sub)`**, где `external_sub` = Firebase `uid` (вариант A) или `sub` из токена провайдера (вариант B);
   - **email** использовать как вспомогательный атрибут; для Apple учесть отсутствие email при повторных входах и private relay.
3. Если пользователя нет — **создать** (аналог текущего поведения OAuth-регистрации): минимум связка с внешним id + email если есть + имя из опционального `display_name` или из claims.
4. Если пользователь есть — **обновить** при необходимости только безопасные поля (например имя), не перетирая критичные данные без правил.
5. Выпустить **`access_token` и `refresh_token`** тем же сервисом, что для OTP (`sub` = внутренний user id, тот же формат claims, что при `verify-otp`).

## 7. Что сделать фронтенду (мобильное приложение) и что передать бэкенду

### 7.1. Что передать бэкенд-команде

| Артефакт | Зачем |
|-----------|--------|
| **Firebase project id** | Совпадение с Admin SDK на сервере. |
| Подтверждение: клиент шлёт **Firebase ID token** | Чтобы бэк выбрал вариант A и `verifyIdToken`. |
| Ожидаемые **sign_in_provider** значения | Например `google.com`, `apple.com` — для логов и политик. |
| Нужен ли в ответе **сырой профиль** как в старом `login-oauth` | Или достаточно JWT + `GET /users/me`. |
| Политика **склейки аккаунтов** | Один email — два провайдера: один пользователь или два (продуктовое решение). |

### 7.2. Что сделать на клиенте после готовности API

1. После успешного `signInWithCredential` вызвать **`getIdToken()`** и отправить токен на **`POST /auth/oauth`**.
2. Сохранить **`access_token` / `refresh_token`** так же, как после **`verify-otp`**.
3. Перевести все запросы User API на **`Authorization: Bearer`** (см. чеклист в [FRONTEND_AUTH_AND_OTP.md §9](./FRONTEND_AUTH_AND_OTP.md)).
4. Убрать вызов **`POST /users/login-oauth`** с телом только `{ email, name, provider }`.
5. Для Apple сохранить текущий UX: при первом входе при возможности передать **имя** в `display_name`, если бэк это поддержит.

---

## 8. Критерии приёмки

- [ ] `POST /auth/oauth` доступен без `pivot-identity-key` и без предварительного Bearer.
- [ ] С валидным Firebase `id_token` возвращается та же структура токенов, что у `verify-otp`.
- [ ] С подделанным / просроченным токеном — предсказуемая ошибка с кодом из §4.4.
- [ ] Повторный вход тем же Firebase `uid` попадает в того же пользователя; первый вход создаёт пользователя.
- [ ] Защищённые маршруты принимают выданный **access** JWT так же, как после OTP.
