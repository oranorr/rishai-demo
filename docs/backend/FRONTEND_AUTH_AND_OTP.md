# Аутентификация, OTP и JWT: руководство для фронтенда

Документ описывает **текущий контракт API** после внедрения OTP на бэкенде, выдачи **access / refresh JWT** и глобальной авторизации запросов. Цель — адаптировать мобильный / web-клиент без сюрпризов.

Подробности доменной логики OTP (коллекции Directus, rate limit, хеширование) см. в [OTP-CODES.md](./OTP-CODES.md) — здесь фокус на **что слать с клиента**.

---

## 1. Модель безопасности в двух словах

| Способ | Заголовки | Когда использовать |
|--------|-----------|-------------------|
| **Новый (рекомендуется после входа)** | `Authorization: Bearer <access_token>` | Пользователь прошёл `verify-otp` или обновил пару через `refresh`. |
| **Legacy** | `pivot-identity-key: <IDENTITY_KEY>` и при необходимости `x-user-id` | Старые сборки / отладка; общий секрет приложения, не персональный логин. |

Бэкенд принимает **или** корректный shared key, **или** валидный **access** JWT (не refresh). Детали ниже.

---

## 2. Публичные эндпоинты (без `pivot-identity-key` и без Bearer)

Эти маршруты помечены как исключения глобального guard — иначе нельзя было бы запросить код и получить первый токен.

| Метод | Путь | Назначение |
|-------|------|------------|
| `POST` | `/auth/request-otp` | Запросить OTP на email. В теле: `{ "email": "..." }`. Код в ответ **не** возвращается. |
| `POST` | `/auth/verify-otp` | Проверить код из письма. Тело: `{ "email": "...", "code": "..." }`. |
| `POST` | `/auth/refresh` | Получить новую пару токенов по refresh. Тело: `{ "refresh_token": "..." }`. |

Остальные маршруты (кроме явных исключений вроде `GET /health`, воркера Cloud Tasks) при включённом на сервере **`IDENTITY_KEY`** требуют либо shared key, либо Bearer access.

---

## 3. Ответ после успешного `verify-otp` и после `refresh`

Форма ответа одинаковая (см. `AuthTokensResponseDto`):

```json
{
  "success": true,
  "access_token": "<JWT>",
  "refresh_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 900
}
```

- **`access_token`** — короткоживущий JWT. Его нужно передавать как **`Authorization: Bearer <access_token>`** для вызовов API «от имени пользователя».
- **`refresh_token`** — долгоживущий; **не** кладите его в заголовок `Authorization` для обычных ручек. Использование: только **`POST /auth/refresh`** в теле JSON.
- **`expires_in`** — оставшееся время жизни access в секундах (ориентир для обновления до истечения).

Рекомендации клиента:

- Хранить **refresh** в защищённом хранилище (Keychain / EncryptedSharedPreferences и т.д.).
- Перед истечением access вызывать **`POST /auth/refresh`**; при ответе **401** на refresh — считать сессию протухшей и вести на повторный OTP.

Переменные окружения бэкенда (TTL), см. `.env.template`: `JWT_ACCESS_EXPIRES_SECONDS`, `JWT_REFRESH_EXPIRES_SECONDS`, опционально `JWT_ISSUER`, `JWT_AUDIENCE`.

## 4. Защищённые запросы: что слать в заголовках

### 4.1. Основной сценарий (после входа)

На каждый запрос к защищённому API:

```http
Authorization: Bearer <access_token>
```

- В поле Bearer указывайте **только строку JWT** (без префикса `Bearer ` внутри значения — его добавляет клиент/SDK/Swagger один раз).
- Используйте именно **`access_token`**, не **`refresh_token`**. Refresh подписан тем же секретом и при ошибочной вставке в Bearer даёт неочевидные 401.

### 4.2. Заголовок `x-user-id`

- Если авторизация **только через Bearer access**: заголовок **`x-user-id` можно не отправлять** — идентификатор пользователя (Directus user id) берётся из поля **`sub`** внутри JWT.
- Если заголовок **`x-user-id` всё же отправлен**, он **обязан совпадать** с `sub` в access-токене — иначе **401** (защита от подстановки чужого id при своём токене).
- Если клиент использует **только `pivot-identity-key`** без Bearer (legacy): **`x-user-id` обязателен** там, где API спрашивает «от какого пользователя» запрос (WHOOP, days, tasks, week-plans и т.д.), потому что shared key не привязан к пользователю.

### 4.3. Legacy: `pivot-identity-key`

Старый контракт сохранён: заголовок **`pivot-identity-key`** со значением, выданным сервером (`IDENTITY_KEY`). При успешной проверке ключа Bearer **не обязателен**.

## 5. Профиль пользователя без id в URL

Добавлены маршруты «текущего» пользователя (id из Bearer `sub` или из `x-user-id` при только identity):

| Метод | Путь |
|-------|------|
| `GET` | `/users/me` |
| `PUT` | `/users/me` |
| `DELETE` | `/users/me` |

Прежние маршруты **`GET|PUT|DELETE /users/:id`** и регистрационные **`POST /users/create`**, **`POST /users/login`** и т.д. **не удалялись** — можно мигрировать постепенно.

---

## 6. Ручки с контекстом пользователя (WHOOP, Days, Tasks, Week plans)

Для эндпоинтов, где раньше требовали **`x-user-id`** на каждый запрос:

- С **Bearer access** достаточно заголовка **`Authorization`**; **`x-user-id` опционален** (см. правила совпадения с `sub` выше).
- С **только `pivot-identity-key`** по-прежнему нужен **`x-user-id`**.

Это относится к контроллерам вроде **`/whoop/*`**, **`/days/*`**, **`/tasks/*`**, **`/week-plans/*`** — клиент может убрать лишние дубли id при работе через JWT.

---

## 7. Формат ошибок

Стандартный ответ об ошибке (глобальный фильтр):

```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "<текст>",
    "statusCode": 401,
    "details": {}
  }
}
```

Типичные сообщения при проблемах с JWT (ориентир для поддержки / логирования на клиенте):

- неверная подпись / истечение access → в духе «Invalid or expired access token»;
- в Bearer случайно передан refresh → явное указание использовать **access_token**;
- несовпадение **`x-user-id`** с **`sub`** при Bearer.

---

## 8. Swagger (неprod)

Если поднят Swagger (`ENVIRONMENT !== production` и задан `SWAGGER_PASSWORD`):

1. Указать схему **Bearer** и вставить значение **`access_token`** целиком (не refresh).
2. При тестировании legacy одновременно можно указать **ApiKey** `pivot-identity-key`.

---

## 9. Чеклист адаптации фронтенда

1. **Убрать** локальную генерацию/проверку OTP; вызывать **`POST /auth/request-otp`** и **`POST /auth/verify-otp`**.
2. После **`verify-otp`** сохранить **`access_token`** и **`refresh_token`**; на API вешать **`Authorization: Bearer <access_token>`**.
3. Реализовать **обновление пары** через **`POST /auth/refresh`** по истечении access или по **401** на защищённых запросах (с осторожностью: не зациклить refresh).
4. Перейти на **`GET /users/me`** (и при необходимости **`PUT`/`DELETE /users/me`**) вместо передачи известного id в пути, если id раньше доставался только после отдельной логики.
5. По возможности **не дублировать** user id: при Bearer не слать **`x-user-id`**, если нет особой причины; если слали всегда — убедиться, что значение **совпадает** с id пользователя из токена (`sub`).
6. Оставить поддержку **`pivot-identity-key`** до полного отказа от старых сборок, если продукт это требует.
