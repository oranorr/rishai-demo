# ТЗ: Recomp (Body Recomp) — пересчёт модификатора на бэкенде

## 1. Цель и контекст

**Body Recomp** — режим фитнес-цели (`goalType = recomp`), при котором калорийная цель задаётся через **`modificator`** (доля от TDEE: `calorieGoal = round((1 + modificator) * tdeeAverage)`).

Продуктовое правило: **модификатор не выбирается пользователем вручную** (в приложении отображается как автоматический), а **через каждые 14 «периодов»** алтернирует между дефицитом и профицитом фиксированной величины **±5%** (`-0.05` ↔ `+0.05`).

Задача ТЗ: **перенести эту логику на бэкенд** (единый источник правды, предсказуемость при нескольких устройствах, отсутствие расхождений с локальным таймером).

---

## 2. Клиент (остаточные договорённости)

Клиент **не** выполняет автоматическую смену `modificator` для recomp — только отображает то, что пришло с бэкенда (профиль пользователя, день, расчёты).

Справочно по данным в приложении:

- Онбординг при выборе Body Recomp задаёт стартовый **`modificator: -0.05`** (`lib/features/onboard/data/questionary_repository.dart`); сервер должен принять/нормализовать это при создании пользователя.
- Допустимые значения recomp в доменной модели: **только** `[-0.05, 0.05]` (`lib/features/user/domain/entities/user_goal_entity.dart`).

Черновик серверного пайплайна дня: `docs/backend/DAY_ENTITY_BACKEND_SPEC.md`, шаг 5. Настоящее ТЗ **уточняет и расширяет** требования.

---

## 3. Данные и инварианты

### 3.1 Поля пользователя (как в клиенте / User Service / Directus)

| Поле | Назначение |
|------|------------|
| `userGoal.goal` / `goalType` | Должен быть `recomp` для активации правил |
| `userGoal.modificator` | Для recomp: **только** `-0.05` или `0.05` (после валидации/нормализации) |
| `userGoal.updatedAt` | **Метка последней смены модификатора по правилам recomp** или начальная установка при выборе цели |

**Требование:** при **любой** смене `modificator` по recomp бэкенд обновляет **`userGoal.updatedAt`** на текущий серверный timestamp (UTC). Это якорь для следующего 14-дневного интервала.

### 3.2 Что не должно сбрасывать таймер recomp

Нужно формально решить на бэкенде (и задокументировать в API):

- Обновление других полей пользователя **без** смены recomp-модификатора **не должно** перезаписывать `userGoal.updatedAt`, если это сломает интервал recomp.
- Если сейчас `updatedAt` шарится с «любым обновлением цели», рекомендуется **вынести отдельное поле**, например `userGoal.recompModifierChangedAt` (или эквивалент), а `updatedAt` оставить общим.  
  **Минимальный вариант для итерации 1:** использовать существующее `updatedAt` **только** как якорь recomp и не менять его при прочих PATCH профиля (либо писать два timestamp’а, если схема позволяет).

*(Уточнить у продукта/аналитики, если `updatedAt` уже семантически означает «любое изменение goal».)*

---

## 4. Алгоритм смены модификатора

### 4.1 Условие применения

Выполнять **только если** `userGoal.goal == recomp`.

### 4.2 Правило переключения

Обозначения: `m` — текущий сохранённый модификатор.

```
newModifier = (m > 0) ? -0.05 : 0.05
```

- Старт с онбординга: `m = -0.05` → следующее значение `+0.05`.
- Если по ошибке в БД `m == 0`, по этой формуле получится `+0.05` (как в клиентском коде). Рекомендуется **нормализовать** некорректные значения для recomp к `±0.05` по последнему известному состоянию или дефолту `-0.05`.

### 4.3 Условие по времени («раз в две недели»)

**Требование:** одна официальная семантика на бэкенде (выбрать и зафиксировать):

| Вариант A | Вариант B |
|-----------|-----------|
| Интервал **`≥ 336`** полных часов от якоря `updatedAt` до **текущего серверного времени** (14×24 ч) | Интервал **`≥ 14`** полных **календарных** дней в выбранной таймзоне пользователя или UTC |

**Рекомендация:** вариант A (детерминированно, без споров про DST и «полдень»).

На бэкенде должна быть **одна** согласованная проверка интервала, без дублирования старых расхождений клиента.

### 4.4 Идемпотентность и гонки

- За один «момент проверки» не более **одной** смены: если условие выполнено, атомарно обновить `(modificator, updatedAt)` (транзакция / compare-and-set по версии или предыдущему `updatedAt`).
- Повторные запросы с тем же состоянием не должны приводить к двойному flip в пределах одного интервала.

---

## 5. Когда выполнять проверку на бэкенде

### 5.1 Основной триггер (обязательно)

В пайплайне **создания нового дня** / пересчёта дня (как в `DAY_ENTITY_BACKEND_SPEC`, «needsCreateNewDay»):

1. Загрузить пользователя с актуальным `userGoal`.
2. Если `goal == recomp` — оценить §4; при смене — **persist** в User Service / Directus.
3. Использовать **уже итоговый** `modificator` для `calorieGoal` и макросов этого дня.

### 5.2 Дополнительный триггер (желательно)

Фоновая задача (cron / очередь), например раз в сутки:

- выбрать пользователей с `goal == recomp` и истёкшим интервалом;
- применить flip, даже если пользователь **не открыл** приложение (консистентность данных и отчётов).

### 5.3 Явный API (опционально)

Эндпоинт вида «синхронизировать recomp» или включение логики в `GET /user` / `PATCH` **не обязателен**, если все потребители проходят через пайплайн дня и cron. Если добавляется — вернуть обновлённый `userGoal` в ответе.

---

## 6. Контракт с клиентом после переноса

1. Клиент **не вычисляет** и **не отправляет** самовольную смену `modificator` для `recomp` (кроме первичного выбора цели при онбординге, если это по-прежнему делается на клиенте — тогда бэкенд валидирует стартовое `-0.05`).
2. Любой ответ, где есть день с целевыми калориями/макросами, должен быть согласован с **текущим** сохранённым `userGoal.modificator`.
3. При смене модификатора на сервере клиент может потребоваться **перезагрузить текущий день** / пересчитать wellness — это отдельная задача фронта (не блокер для бэкенда, но указать в релиз-нотах).

## 7. Логирование и наблюдаемость

- Структурный лог: `userId`, старый/новый `modificator`, старый/новый `updatedAt`, причина (`new_day_pipeline` | `scheduled_job` | `manual_admin`), результат (changed / skipped / not_recomp).
- Метрика: количество flips за период; алерты на аномально частые смены для одного пользователя.

---

## 8. Критерии приёмки

- [ ] Для пользователя с `goal=recomp` после истечения выбранного интервала (§4.3) при следующем **создании дня** модификатор меняется на противоположный `±0.05`, `updatedAt` обновляется, день считается с новым `calorieGoal`.
- [ ] Повторный пересчёт за тот же период **не** дублирует flip.
- [ ] Два параллельных запроса **не** приводят к двойному flip (корректная конкуррентность).
- [ ] Пользователь с целью **не** recomp не затрагивается.
- [ ] Некорректные значения `modificator` для recomp обрабатываются предсказуемо (нормализация или ошибка с кодом).
- [ ] Документ `DAY_ENTITY_BACKEND_SPEC.md` шаг 5 приведён в соответствие с финальной семантикой времени (A или B) и полем-якорем (`updatedAt` vs отдельное поле).
