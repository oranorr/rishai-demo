# ТЗ: интеграция OAuth на фронтенде с бэкендом (`POST /auth/oauth`)

Документ для мобильной / web-команды: что подготовить и как переключить вход через Google / Apple на **криптографически проверяемый** токен Firebase и **ту же пару JWT**, что после email+OTP.

Связанные документы:

- [FRONTEND_AUTH_AND_OTP.md](./FRONTEND_AUTH_AND_OTP.md) — публичные `/auth/*`, Bearer, формат ошибок, `GET /users/me`
- [OAUTH_BACKEND_TZ.md](./OAUTH_BACKEND_TZ.md) — контекст и критерии приёмки на бэкенде

---

## 1. Цель

1. После нативного входа (Google / Apple) и **Firebase Auth** (`signInWithCredential` / аналог) клиент получает **Firebase ID token** и обменивает его на **`access_token` / `refresh_token`** бэкенда приложения.
2. Дальше все запросы к User API и связанным модулям — с **`Authorization: Bearer <access_token>`**, без опоры на «доверие к телу» `{ email, name, provider }` и без обязательности **`pivot-identity-key`** для этого шага входа.
3. Постепенно отказаться от **`POST /users/login-oauth`** в текущем виде (legacy, deprecated в Swagger на бэкенде).

---

## 2. Предусловия (что должно быть согласовано до релиза)

| Артефакт | Зачем |
|----------|--------|
| **Один Firebase project** на клиенте и на бэкенде | Иначе `id_token` не пройдёт `verifyIdToken` на сервере |
| На бэкенде настроен **Firebase Admin** (секрет с JSON сервисного аккаунта) | Без этого **`POST /auth/oauth`** вернёт **503** |
| Базовый URL API (staging / prod) | Для вызова `/auth/oauth` и дальнейших ручек |

Фронту **не нужно** знать содержимое сервисного аккаунта — только убедиться, что деплой бэка с секретом выполнен до включения фичи в приложении.

---

## 3. Контракт API

### 3.1. Эндпоинт

| Метод | Путь | Аутентификация запроса |
|--------|------|-------------------------|
| `POST` | `/auth/oauth` | **Без** `pivot-identity-key`, **без** Bearer до получения токенов |

Этот маршрут в том же классе публичных ручек, что `request-otp`, `verify-otp`, `refresh` (см. [FRONTEND_AUTH_AND_OTP.md §2](./FRONTEND_AUTH_AND_OTP.md)).

### 3.2. Тело запроса (JSON)

| Поле | Обязательность | Описание |
|------|----------------|----------|
| `id_token` | **Да** | Строка **Firebase ID token** после успешного входа (например `getIdToken()` в Firebase SDK) |
| `provider_hint` | Нет | Например `"google"` / `"apple"` — **только для логов на бэке**, на авторизацию **не влияет** |
| `display_name` | Нет | Имя с клиента (актуально для **первого** Apple sign-in, когда имя может прийти только на клиенте); повторные входы могут обходиться без поля |

Пример:

```json
{
  "id_token": "<Firebase ID token JWT>",
  "provider_hint": "google",
  "display_name": "Jane"
}
```

Минимальный запрос:

```json
{
  "id_token": "<Firebase ID token JWT>"
}
```

### 3.3. Успешный ответ

Идентичен ответам **`POST /auth/verify-otp`** и **`POST /auth/refresh`**:

```json
{
  "success": true,
  "access_token": "<JWT>",
  "refresh_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 900
}
```

Семантика полей — в [FRONTEND_AUTH_AND_OTP.md §3](./FRONTEND_AUTH_AND_OTP.md).

### 3.4. Ошибки

Формат конверта — в [FRONTEND_AUTH_AND_OTP.md §7](./FRONTEND_AUTH_AND_OTP.md): `success: false`, объект `error` с `code`, `message`, `statusCode`.

Типичные случаи для `/auth/oauth`:

| HTTP | Когда |
|------|--------|
| **401** | Невалидный / просроченный `id_token`; или email в Firebase **не** помечен как подтверждённый (`email_verified`) — см. §5 |
| **400** | Нет `id_token`, пустое тело, валидация DTO; или в токене **нет email** при текущей политике бэка (email-first) |
| **503** | На сервере не настроен Firebase (нет / битый `FIREBASE_SERVICE_ACCOUNT_JSON`) |

При необходимости в ответе может быть кастомное поле `error.code` (например для невалидного токена) — обрабатывать похоже на остальные auth-ошибки.

## 4. Поток на клиенте (обязательная последовательность)

1. Пользователь проходит нативный OAuth (Google / Apple).
2. Подключение к **Firebase Auth** (`signInWithCredential` или принятый в проекте аналог).
3. После успешного Firebase-сеанса получить **свежий** **Firebase ID token** (например `getIdToken()`; при необходимости `getIdToken(true)` для принудительного обновления — по политике SDK).
4. Выполнить **`POST {API_BASE}/auth/oauth`** с JSON из §3.2.
5. Сохранить **`access_token`** и **`refresh_token`** в том же слое хранения и с той же политикой обновления, что после **`verify-otp`**.
6. Все последующие вызовы защищённого API:
   - заголовок **`Authorization: Bearer <access_token>`**;
   - см. правила **`x-user-id`** в [FRONTEND_AUTH_AND_OTP.md §4](./FRONTEND_AUTH_AND_OTP.md).
7. Профиль «текущего пользователя» — **`GET /users/me`** с Bearer (минимальный контракт после логина; отдельное тело профиля в ответе `/auth/oauth` не требуется).

**Явно не делать** на запросе `/auth/oauth`:

- не требовать и не навязывать **`pivot-identity-key`**;
- не подставлять **`refresh_token`** в заголовок `Authorization` для обычных ручек.

## 5. Ограничения текущей модели на бэкенде (важно для UX)

Сейчас маппинг пользователя на бэкенде — **email-first**:

- В Firebase ID token должны быть **email** и флаг **`email_verified: true`**. Иначе вход через `/auth/oauth` будет отклонён.
- Если у провайдера (часто **Apple**) при повторном входе **нет email** в токене, пользователь может получить **400** с сообщением о невозможности email-first входа. Продуктово заложить:
  - сообщение пользователю;
  - при необходимости отдельный трек на бэкенде: хранение `(provider, external_sub)` / Firebase `uid` в Directus (вне рамок этого ТЗ для фронта, но влияет на долгосрочный UX).

Рекомендация клиента: при первом Apple sign-in по возможности передавать **`display_name`**, если оно доступно только на устройстве.

## 6. Миграция со старого потока

| Было | Стало |
|------|--------|
| После Firebase вызывать **`POST /users/login-oauth`** с `{ email, name, provider }` и часто с **`pivot-identity-key`** | После Firebase вызывать **`POST /auth/oauth`** с `{ id_token, ... }` **без** identity key |
| Опора на то, что бэк «доверяет» email из тела | Идентичность подтверждается **verifyIdToken** на сервере |

План выката:

1. Добавить вызов `/auth/oauth` и сохранение пары JWT.
2. Переключить API-клиент на Bearer после успешного OAuth.
3. Убрать вызов `login-oauth` в новых версиях приложения (оставить за feature-flag / версией до отказа от старых сборок).

---

## 7. Критерии приёмки (фронт)

- [ ] После Google и Apple (в тестовых аккаунтах с валидным email и `email_verified`) **`POST /auth/oauth`** возвращает **200** и ту же структуру, что `verify-otp`.
- [ ] **`GET /users/me`** с выданным **access** возвращает ожидаемый профиль.
- [ ] Обновление пары через **`POST /auth/refresh`** с сохранённым **refresh** работает так же, как после OTP.
- [ ] При истечении / отзыве сессии обработаны **401** на refresh и показан понятный сценарий повторного входа.
- [ ] Старый путь `login-oauth` не используется в новой логике или зафичерфлажен.

---

## 8. Что подготовить заранее (чеклист разработки)

1. **Слой API**: метод `exchangeOAuthToken(idToken, options?)` → `POST /auth/oauth`.
2. **Auth state**: единая модель сессии после OTP и после OAuth (одни и те же поля access/refresh/TTL).
3. **Интерцептор HTTP**: подстановка Bearer; не смешивать refresh в Bearer.
4. **Обработка ошибок** §3.4 + ревокация локальной сессии при «невалидный токен».
5. **Apple**: сохранение и однократная отправка `display_name` при первом показе, если продукт это требует.
6. **Согласование с бэком**: включён ли уже секрет Firebase на нужном окружении (staging до prod).
